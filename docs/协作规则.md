# 协作规则

更新时间：2026-04-01

## 目标

本文件定义本项目的固定协作方式，用于约束后续所有任务执行，避免范围漂移、信息丢失和新设备接手断层。

## 记录语言

- 默认使用中文记录需求、执行说明、验证结论、交接信息。
- 仅在技术标识必须保持英文时使用英文，例如路径、命令、变量、提交哈希。

## 范围控制

- 未明确要求的内容不改。
- 改动前先给出范围边界：改什么、不改什么、预计涉及哪些文件。
- 如果执行中发现必须扩展范围，先说明原因再扩展。
- 若出现范围外改动，必须在交付时明确反馈。

## 执行与复查

- 改前核查：先确认用户提出的问题是否属实，再实施改动。
- 改后复查：按需求逐条验证，不得只做局部验证。
- 若验证条件不足，必须明确标注“未验证项”。

## 多任务与多 agent

- 当请求同时包含两个及以上可并行推进的独立工作流时，自动启用多 agent。
- 常规使用 2 个 agent；复杂并行场景最多 3 个，避免协调成本反噬效率。
- 不要求用户手动提醒，默认由执行侧自动判断是否需要多 agent。

## Git 与发布前检查

- 推送 Git 前必须完成最小可行验证。
- 提交说明必须聚焦本次任务，不混入无关变更。
- 发现环境问题（链路、权限、缓存）需单独记录，不与功能改动混写。

## 文档同步硬要求

- 每次任务完成后，至少同步更新以下文件：
- `change-logs/`（新增当次日志）
- `docs/当前状态.md`
- `docs/最新交接.md`
- 若协作方式、环境或发布策略变化，再同步更新以下文件：
- `docs/协作规则.md`
- `docs/环境与发布.md`

## 风险反馈

- 发现 skill 不适用、长期低频使用、或明显增加执行成本时，必须主动反馈并给出调整建议。
- 发现重复性流程问题，优先沉淀为可复用规则或 skill 条目。
